# BieberKit 0.2.0 beta

Prepared for the first real npm beta. Package version: **0.2.0** for all 26 packages and plugins. npm dist-tag: **beta**. Release git tag: **v0.2.0-beta**. The version has no prerelease suffix (PLG-08, ADR 0014). The reserved 0.0.1 placeholders are not framework releases.

## Highlights

- The framework provides declarative entities, REST APIs, the admin foundation, authentication, authorization, audit logging and contracts for background jobs, mail, cache and storage.
- Base-plugin platform S0 adds `disableUser` and `enableUser`, transactional session revocation and audit entries. Disabled accounts are refused across sign-in, cookie and API-key paths. Cached sessions cannot return after enable, and session issuance is serialized with disable.
- Auth users gain disabled-status and provider-identity columns. External identifiers are unique within their provider; new users default to `local`.
- Typed `mail`, `queue` and `cache` services are available to every process role, seeders and the test app. Reset and verification mail written inside a transaction uses the outbox and is delivered after commit.
- Modules contribute outbox-to-job subscriptions. Duplicate events fail with `QUEUE_SUBSCRIPTION_DUPLICATE`, and unregistered jobs fail with `QUEUE_JOB_UNKNOWN`. Failed initialization releases acquired resources.
- `createTestApp` exposes an in-memory `mailbox` and explicit `runOutbox()` delivery.

Package changelogs were generated from `auth-profile` and `platform-services`. The fixed release group advances every package together, including packages with no direct source change.

## Upgrade and deployment

After publication, install with `pnpm add @bieberkit/core@beta`, or scaffold with `pnpm create bieberkit@beta my-app`. Generated projects enforce a seven-day release age (SEC-11).

Run the normal deployment migrations before starting application roles. The new auth columns are six additive migration steps identified as **0.5.0** by the auth migration history; that step version is separate from the **0.2.0** npm package version. No destructive migration is required.

Web processes may enqueue database-backed jobs without running a worker. Run a worker to deliver committed outbox events and authentication mail.

## Beta scope

Base-plugin slices S1–S6, the production Pilot and the phase acceptance gates remain open. Admin and base plugins have the scope recorded in the roadmap; this beta does not declare the project production-ready or complete those gates.

## Local verification

Verified with Node.js 26.13.1 and pnpm 12.21.0:

- `pnpm build`, `pnpm check`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` and `pnpm check:api` passed (56 API reports).
- `pnpm test --maxWorkers=2 --testTimeout=15000`: **3234 passed, 317 skipped; 218 files passed, 1 skipped**, 192.21 s. The skip count is the suite output for the default local configuration.
- `pnpm test:artifacts`: **2 passed**.
- `pnpm check:packages`: **26 tarballs passed** publint and attw with the ESM profile.
- All 26 prepared tarballs contain their changelog and version 0.2.0, with internal workspace dependencies resolved to 0.2.0. The publish order and all 27 SHA-256 entries (tarballs plus publish order) were verified.

These local checks do not supply the GitHub/OIDC evidence required below.

## Publication handoff

1. Review and merge the version-preparation branch into `main` after CI passes.
2. Complete the first GitHub release dry run from [the release runbook](../releasing.md#the-first-dry-run). OIDC, provenance, protected tags and environment approval still need end-to-end evidence; their roadmap items remain open.
3. Create the signed tag `v0.2.0-beta` on that `main` commit, push the tag and approve the `release` environment only after `verify` and `build` pass.
4. Check the published version, npm `beta` tag and provenance. The preparation step does not publish packages or create a release tag.
