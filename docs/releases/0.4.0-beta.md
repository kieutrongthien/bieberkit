# BieberKit 0.4.0 beta

Package version: **0.4.0** for all 26 packages and plugins. npm dist-tag: **beta**. Release git tag: **v0.4.0-beta**. The version has no prerelease suffix (PLG-08, ADR 0014).

## Highlights

- **Each plugin ships its own screens.** A project builds one admin from the admin parts of its plugins, in ten fixed slots (ADR 0040). The shared packages hold no screen of one plugin.
- **Writing a plugin.** `bieberkit make:plugin` makes a backend and a page in the admin, wires them into the project, and `pnpm dev` follows their code. See [writing a plugin](../guides/writing-a-plugin.md).
- **Account screens:** the sign in with a second factor, a forgotten password, an invitation, setting up a second factor, and one's own profile, password, factor and sessions.
- **A new look of the admin:** a grouped menu, a breadcrumb, a box that goes to a page, and the name, logo and menu order of a project through the `admin` key of the config.
- **`@bieberkit/content`** has its first API: rich content as blocks, drawn as HTML or as React elements (ADR 0038).

The package changelogs hold the full list.

## Fixes

Found with packed packages in a project outside the repository:

- A new project failed `bieberkit build` on two type errors, and `bieberkit migrate` because its root did not declare `@bieberkit/data`. `0.3.0` has this code.
- `migrate:make` wrote a file with no header, which `bieberkit check` refused.
- The image of the generated `Dockerfile` could not start: the config at its root found no `node_modules`.

## Breaking changes

| Area                | Change                                                                                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin               | There is no prebuilt admin. A project has `apps/admin` and builds it with `bieberkit build`. The web role does not start with an `apps/admin` that is not built (`BK_ADMIN_NOT_BUILT`). |
| Screens of a plugin | `definePlugin({ admin })`, the folder `admin` served under `/plugins/` and `@bieberkit/admin-antd` in `apps/server` are gone. A plugin gives screens through its export `./admin`.      |
| `_meta`             | `schemaVersion` is 2. `extensions` and `menu` are gone.                                                                                                                                 |
| `admin-core`        | `AdminClient` lost `signIn`, the calls of the account, of files and of the history, with their functions and message keys. It gained `request()`.                                       |
| Audit log           | The history tab of a record is shown only to a person with `audit-log.read`.                                                                                                            |
| Theme               | The default theme changed, with two new colors, `frame` and `accent`, and a default radius of 10. A `Theme` or `ThemeColors` made by hand has to give both colors.                      |

## Behavior that changes

- The server turns TOTP on. Nobody has to set it up unless a role or the security policy asks for it.
- A password that is set through a link ends every session of the account, and turning the second factor on ends every other session.
- With an admin, the links of an invitation and of a password reset by an administrator lead to `<admin>/reset-password`.

## Upgrade a project

Make a new project with `pnpm create bieberkit@beta` at this version beside yours, then:

1. Copy its `apps/admin` folder into yours, keep your name in `apps/admin/package.json`, and add every plugin of your config to its `dependencies`.
2. Remove `@bieberkit/admin-antd` from `apps/server/package.json`.
3. In `pnpm-workspace.yaml`, add `dedupePeerDependents: false`, and list `'plugins/*'` if you hold plugins there.
4. In the root `tsconfig.json`, add `"apps/admin"` and `"plugins/*/src/admin"` to `exclude`, and `"plugins/*/src/**/*.ts"` to `include`.
5. Copy its `Dockerfile` and `deploy/image.mjs`, or add their two new lines to yours.
6. Move the screens that a plugin of yours declared in `definePlugin({ admin })` into its `./admin` export.
7. For a project made with `0.3.0`: add `@bieberkit/data` to the `devDependencies` of its root, and give the default export of `bieberkit.config.ts` a type: `const config: ProjectConfigInput = defineConfig({ ... }); export default config;`.
8. Run `pnpm install`, then `pnpm bieberkit build`.

No table changed since `0.3.0`, so this release asks for no migration. Generated projects enforce a seven-day release age (SEC-11).

## Local verification

Run on 2026-11-28 with Node.js 26.13.1 and pnpm 12.21.0.

On the tree of this release, with the versions at `0.4.0`: `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm check` and `pnpm format:check` passed.

On the tree before the version bump (`df6a6b7`, version `0.3.0`) or shortly before it. **None of these tests were run again at `0.4.0`:**

- `pnpm test`: **4109 passed, 365 skipped; 283 files passed, 1 skipped**. No external services were started, so the PostgreSQL and MySQL cases were skipped. The three-dialect run has not run since the account screens, and Node.js 24.12 was not run.
- `pnpm test:e2e`, before the last fix (`df6a6b7`): **55 passed, 1 failed, 6 not run** after it in its file. The failure is the contrast of the hover color of a default button (3.77:1), older than this release. Seven of the other accessibility cases passed in a run of their own; the "relation picker" case, which fails on contrast most runs, was left out. After the last fix, `slots.spec.ts` and `account.spec.ts` passed (21 cases).
- Before the last fix: `pnpm test:acceptance` (18 steps), `pnpm test:artifacts` (5 passed), `pnpm check:packages` (26 tarballs) and `pnpm check:api` (61 reports) passed.

Not run: a real `docker build` of a project, and CI. These local checks do not supply the GitHub/OIDC evidence of a release.

## Publication handoff

1. Push `main` and let CI pass.
2. Create the tag `v0.4.0-beta` on that `main` commit, push the tag and approve the `release` environment only after `verify` and `build` pass ([the release runbook](../releasing.md)).
3. Check the published version, npm `beta` tag and provenance. The preparation step does not publish packages or create a release tag.
