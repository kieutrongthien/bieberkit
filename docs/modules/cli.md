## Behavior of C1

1. **One function runs it.** `runCli(argv, io)` answers the exit code. `bin.ts` gives it the real streams and sets `process.exitCode`, and a test gives it arrays. Nothing in the CLI reads `process.env` (P8): a command that needs the environment gets it from core, which reads the real one unless a test passes a source.
2. **Exit codes (section 5.3).** `0` success, `1` failure, `2` the command was used wrongly (unknown command, unknown flag, a flag without its value, a missing or an extra argument), `3` a check found violations (`env:example --check` when the file is stale).
3. **`--json` on every command (AI-03).** One document on stdout: `{ "ok": true, "command", "data" }`, or `{ "ok": false, "command", "error": { code, message, fix, docs, exit, problems? } }`. A check that finds violations is `{ "ok": false, "command", "data" }` with exit code 3. Progress goes to stderr, so stdout can always be parsed. The same answer without `--json` is text, and a failure is text on stderr: `error[CODE]: message`, each problem, `fix:` and `docs:`.
4. **Stable codes (AI-02).** A failure of the CLI has a code that starts with `BK_`: `BK_USAGE_UNKNOWN_COMMAND` (with the nearest command when it is within two edits), `BK_USAGE_UNKNOWN_FLAG`, `BK_USAGE_FLAG_VALUE`, `BK_USAGE_MISSING_ARGUMENT`, `BK_USAGE_UNEXPECTED_ARGUMENT`, `BK_PROJECT_NOT_FOUND`, `BK_PLUGIN_NOT_INSTALLED`, `BK_PLUGIN_NOT_EXPORTED`, `BK_PLUGIN_OPTIONS` and `BK_UNEXPECTED`. An error of the framework keeps its own code (`CFG_ENV_MISSING`, `CFG_CONFIG_INVALID`, `PLG_CYCLE`), and a list of problems (the env, the config, the plugins) is kept as `problems`, each with its key. An error that is not ours or the framework's is `BK_UNEXPECTED` with its message and never its stack. The link is `https://bieberkit.dev/docs/errors/<CODE>`; the address is one constant (`DOCS_BASE`) until the documentation site exists.
5. **The project loader.** A command finds `bieberkit.config.ts` in the working directory or above it (`--cwd` changes the directory), reads it (Node strips the types), checks it with `validateConfig`, loads each plugin that it lists from `node_modules` (the default export of its main file, as in section 11.2), checks its options with the parser that the plugin declared, and resolves the graph with `resolvePlugins` against the real version of core and the dialect of the project. The result is the plugins in boot order.
6. **`plugins`** lists them in boot order with version and requirements.
7. **`env:check`** validates the environment against the merged schema of core and the plugins, reading `.env` of the project and then the real variables (the real ones win, CFG-03). Every problem is reported together.
8. **`env:example`** prints `.env.example` (core first, then the plugins in boot order, a description and what a key takes above each key). A secret never shows its value or default (CFG-06). `--write` writes the file only when it differs, and `--check` exits with 3 when it is missing or out of date, so CI can keep a committed generated file honest (GEN-01). The same schema gives the same bytes (GEN-03).
9. **No telemetry.** The CLI sends nothing anywhere.

## Behavior of C2: `bieberkit check [rule]`

1. **Rules.** `headers`, `env-access`, `boundaries`, `orm`, `sql`, `transactions`, `migrations`. `bieberkit check` runs all, and `bieberkit check <rule>` one (an unknown name is `BK_USAGE_UNKNOWN_RULE`, exit code 2). The answer lists each violation with `file:line`, its `BK_` code, the message, the fix and a link, and ends with the counts. With `--json`, `data` has `rules`, `files`, `errors`, `warnings` and `violations`.
2. **Exit code 3** when there is an `error`. A `warning` is shown and the exit code stays 0: the escape hatches of ADR 0009 (`*.orm.ts` and `orm: { ... }`) and a migration that cannot be read are warnings.
3. **What is read.** Every source, style, SQL and YAML file of the project, in the order of the paths, without `node_modules`, builds, `.git`, `.bieberkit` and caches, and the rules about code skip tests and generated files (those that say `@generated`, GEN-01).
4. **No parser, on purpose.** `maskCode` hides comments and the text of strings and templates and leaves the code of `${ }`, with every offset and line where it was, so a pattern can only match code. A pattern that has to read a string (the specifier of an import, `process['env']`) matches only when its first character is code. A rule is a pattern and a call-closing search, which is small enough to read, test and port to the Oxlint plugin of C6. What it cannot see (a call through an alias) it does not claim.
5. **`headers` (HDR-01, HDR-02, section 23.7).** A source file starts, after a shebang, with the block comment that has `@file` (its path from the root), a `@description` that is not empty, the `@author` and the `@license` of `bieberkit.config.ts`. Codes: `BK_HEADER_MISSING`, `BK_HEADER_FILE`, `BK_HEADER_DESCRIPTION`, `BK_HEADER_AUTHOR`, `BK_HEADER_LICENSE`. Declaration files and generated files are left out.
6. **`env-access` (P8).** `process.env`, `process['env']`, a named import or a destructure of `env` from `process`, `process.loadEnvFile` and `import.meta.env` are `BK_ENV_ACCESS`. The `*.config.*` of a tool (`vite.config.ts`) may read the environment, and `bieberkit.config.ts` may not.
7. **`boundaries` (MOD-01, PLG-01, PKG-03).** `BK_BOUNDARY_MODULE`: a file of `modules/a` imports a file of `modules/b` other than its `index`. `BK_BOUNDARY_PLUGIN`: an import of `<plugin>/<sub>` that the plugin does not export (read from its `package.json`, where an `exports` key may be a pattern with `*`, and `src`, `dist`, `lib` and `internal` when it is not installed), or a relative path, inside the project or through `node_modules`, into the files of another plugin package that are not the entry of its `.` export. A package is a plugin by its name (PLG-05), by the keyword `bieberkit-plugin` or by its static manifest (PLG-07), and a plugin may import its own files by its own name. `BK_BOUNDARY_TOOLS`: the project imports `bieberkit`, `create-bieberkit` or `@bieberkit/mcp`; the one exception is `bieberkit/admin-vite` in a `vite.config` file, which the build of `apps/admin` reads (UI-37). `BK_BOUNDARY_DRIVER`: the project imports a driver library (BullMQ, BentoCache, FlyDrive, ioredis, pg, nodemailer, a search engine, Sentry).
8. **`orm` (SCH-08, ADR 0009).** `BK_ORM_IN_ENTITY` (error): a file with `defineEntity` imports `@mikro-orm/*` or `kysely`. `BK_ORM_OVERRIDE` and `BK_ORM_HANDWRITTEN` (warnings): `orm: { ... }` in an entity, and a `*.orm.ts` file.
9. **`sql` (SEC-05).** `BK_SQL_STRING_BUILT`: `sql.raw`, `.raw`, `.execute` or `.query` whose first argument is a template with `${ }` or text joined with `+`. The `sql` tag with values, a fixed statement and a statement with parameters pass.
10. **`transactions` (WP-01).** `BK_TX_EXTERNAL_CALL`: inside `runInTransaction`, `runInUnitOfWork` or `.transactional`, a call to `http.fetch`, `fetch`, `mail.send`, `mailer.sendNow` or `queue.dispatch`. The fix is an outbox event.
11. **`migrations` (DATA-08).** `BK_MIGRATION_DESTRUCTIVE`: the `up()` of a migration drops or renames a column or table, changes a type, or adds a `not null` column with no default (`detectDestructive` of `@bieberkit/data`).
12. **A deliberate exception.** `// bieberkit-ignore BK_CODE: the reason` on the line of the violation or the line before lets one violation through. The reason is required, and a directive with no reason does not count.
13. **Not in C2.** The route permissions (they need the routes that C3 loads), the stale generated files (they need the generators of C3), and the Oxlint plugin (C6).

## Behavior of C3

1. **The application without starting it.** `loadApp` loads the project, the modules of its plugins in boot order and the modules of the project (`apps/server/src/modules/<name>/module.ts`, whose default export is `defineModule`, section 7.4), takes their `entities` and `routes` contributions, makes the routes of the entities with `entityRoutes` over a database in memory (nothing connects anywhere), and keeps the routes of the modules. A module file that does not export a module is `BK_MODULE_NOT_EXPORTED`.
2. **`routes`** prints the method, the path and the permission (or `public`) of each route, sorted by path and method.
3. **`openapi`** prints the OpenAPI 3.1 document, or writes it with `--out <file>`. The same routes give the same bytes (GEN-03).
4. **`generate`** writes, and only when the content differs: `.bieberkit/types/entities.d.ts` (the `EntityRegistry` of SCH-04), `.bieberkit/schemas/<entity>.<create|update|read>.json`, `.bieberkit/meta/plugins.json` (the resolved graph), `.bieberkit/openapi.json`, and `packages/client/`. `client:generate` writes only `packages/client/`. With `--check` they write nothing and exit with 3 when a file is missing or differs. The Zod Mini side of section 10.6 is built at run time from the same definitions (`toZodMini`), so it has no file.
5. **Generated headers (HDR-05).** The layout of section 23 with `@generated <command>` and no copyright year, because a year that changes would make every file stale on 1 January (GEN-03). `bieberkit check` leaves generated files out of the rules about code, and the rule `generated` compares the committed ones (`packages/client/`) with what the generators give now: `BK_GENERATED_STALE` (GEN-01).
6. **The typed client (API-07).** `packages/client/src/index.ts` has the types of the API, `ApiError` (the status and the problem of RFC 9457), `ClientOptions` (`baseUrl`, `fetch`, `headers`, `credentials`), the interface `Client` with a typed function for each operation (`getCrmPeople({ query })`, `patchCrmPeopleById({ path, headers, body })`), and `createClient`. A query object is written as `filter[name][eq]=Ann`, a path value is encoded, `204` is `undefined`, and an answer that is not a success throws `ApiError`. The file compiles under `strict`, `isolatedDeclarations`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess` and `erasableSyntaxOnly` (a test runs the compiler on it). Query hooks come with the admin.
7. **Rules added to `check`.** `routes`: `BK_ROUTE_NO_PERMISSION` for a route that has neither a permission nor `public: true` (API-02). `generated`: `BK_GENERATED_STALE`. A project whose application cannot be loaded is one violation, `BK_APP_UNLOADABLE`, and not a crash of the whole check. DATA-07 needs no rule: a filter or a sort on a field with no index is refused by the query itself (`DATA_QUERY_*`, with the fix `.index()`).
8. **Recipes.** `make:module <name>` writes `modules/<name>/module.ts` with the markers `bieberkit:imports`, `bieberkit:entities` and `bieberkit:jobs`. `make:entity <module>.<Name> [--tenant]` writes `entities/<name>.ts` (a name, an id, the five routes) and registers it above the markers. `make:job <module>.<name>` writes `jobs/<name>.ts` and registers it. A file that exists is `BK_MAKE_EXISTS`, a module that does not is `BK_MAKE_MODULE_MISSING` (with the command to run), a name that is wrong is a usage error (exit code 2), and a module whose marker was edited away still gets the file, with `BK_MAKE_UNREGISTERED` and the two lines to add by hand. The files carry the header of the project with the year of today (HDR-03). `module.ts` is the public entry of a module, so another module may import it (rule `boundaries`).

## Behavior of C4: `create-bieberkit <name>` and `bieberkit create <name>`

1. **One kit, two programs.** The arguments, the failures with stable codes, the shape of a command and the runner with `--json` and the exit codes live in `create-bieberkit/kit`, so that the scaffolder and the CLI fail and answer alike, and `pnpm create` downloads a package with one dependency (core), not the whole CLI. `bieberkit` depends on `create-bieberkit` and registers the same command under the name `create`, as the alias of section 5.1.
2. **Every prompt has a flag.** `--db`, `--template`, `--plugins`, `--admin/--no-admin`, `--site/--no-site`, `--author`, `--license`, `--install/--no-install`, `--git/--no-git`, `--yes`, `--json`. A choice comes from its flag, then from a prompt when a person is at the terminal (and `--yes` and `--json` were not given), then from the default with `--yes` (`sqlite`, `blank`, the author of git config), and otherwise the command stops with `BK_CREATE_CHOICE_NEEDED` and lists every flag that is missing, exit code 2.
3. **A check before a write (section 6, steps 1 to 5).** The name is an npm package name (`BK_CREATE_NAME_INVALID`), the folder does not exist or is empty (`BK_CREATE_TARGET_NOT_EMPTY`), the database, the template, the author (`Name <email>`) and the license (an SPDX identifier) are valid, every plugin is one that the scaffolder knows (`BK_CREATE_PLUGIN_UNKNOWN`), and the graph resolves with the resolver of core on the manifests that `create-bieberkit` carries, so the codes are those of section 11.2 (`PLG_MISSING_REQUIRE`, `PLG_CONFLICT`, `PLG_DIALECT`...). Only then are files written, and a write that fails removes what it made.
4. **Templates and plugins are data.** A `Template` is a name, a list of plugins, a tenancy mode, locales and whether it has a site. `blank` ships with no plugins, because the base plugins are built in M1.8, and `cms`, `crm` and `saas` are not offered until their plugins exist. The index of first-party plugins (version and manifest) is empty for the same reason. Adding a template or a plugin changes data and no code of the scaffolder.
5. **The files.** `package.json`, `pnpm-workspace.yaml` (the settings of SEC-11, `better-sqlite3` allowed to build only on SQLite), `tsconfig.json`, `bieberkit.config.ts`, `.env` (development defaults and fresh secrets, never committed), `.env.example` (every key, no secret), `compose.yaml` (the database of the choice, a Valkey with `noeviction` and one for the cache with `allkeys-lru`), `.gitignore`, `AGENTS.md`, `CLAUDE.md`, `apps/server/package.json`, `apps/server/src/main.ts`, `data/.gitkeep` on SQLite, and `LICENSE` for MIT, ISC, BSD-2-Clause, BSD-3-Clause and Apache-2.0 (`UNLICENSED` and an identifier that is not known write none). Each file with comments carries the header of section 23.7: the name of the project, its own path, the author and the license of the project, and the year of the day.
6. **`.env` is valid.** A test reads what the scaffolder wrote with `readCoreEnv`, on each dialect, and a project made by it passes `env:check`, `env:example --check`, `generate` and `check`, and takes `make:module` and `make:entity`.
7. **Install and the first commit (steps 8 and 11).** `pnpm install` runs in the folder, then `git init -b main`, `git add -A` and a commit signed by the author of the project, so it works on a machine with no git identity. A step that fails does not remove the files: it is a `problem` of the result and the exit code is 1, and the commit is still made.
8. **Not in C4.** The apps of the admin and the site (M1.8 and Phase 2: the result says so), the real `main.ts` that boots the roles (C5), the first migration and the administrator seed (they need the base plugins), and `.agents/skills`.

## Behavior of C5

1. **Where the code is.** The process lives in `@bieberkit/server` (ADR 0024), which a project may import and a tool may not. `start` and `dev` run `apps/server/src/main.ts` (or `apps/server/dist/main.js` when it was built) in a child process of this CLI, so that the signals of the terminal reach the server and its exit code is the exit code of the command. `docs/modules/server.md` has the boot.
2. **`start <role>`** runs `node <entry> <role>` for `web`, `worker`, `scheduler` or `migrate`. A name that is not a role is `BK_USAGE_UNKNOWN_ROLE` (exit code 2), and a process that fails ends the command with 1.
3. **`dev`** writes the generated files (GEN-02), starts the services of `compose.yaml` with `docker compose up -d` (a failure is a message, because the development defaults need none; `--no-services` skips it), then runs `node --watch <entry> dev`: web, worker and scheduler in one process, with the tables made first. A change under `apps/server/src` regenerates the files 300 ms after the last change.
4. **`db:seed`** runs the seeders and says which ran. **`doctor`** prints one line for each check (`ok`, `warning` or `error`, with the fix), and an error is `BK_DOCTOR_FAILED` with the fixes, exit code 1.
5. **`test [filter] [--watch] [--coverage]`** writes `.bieberkit/vitest.config.ts` and `.bieberkit/vitest.setup.ts` (part of `generate`, not committed) and runs `pnpm exec vitest` with them. The preset includes `apps/**` and `packages/**` tests, provides the URLs of the test databases from the environment the way CI gives them, and installs the guard on the network of `@bieberkit/testing` (TST-03).
6. **A new project starts.** The test of this slice makes a project with `create`, links the packages of the repository where `pnpm install` would, starts its `main.ts web` in a real process on free ports, waits for `/health/ready` and the metrics, and stops it with SIGTERM: exit code 0.
7. **Left for M1.8.** The first migration and the administrator seed need the base plugins; the commands `migrate:make`, `migrate` and `build` are C7.

## Behavior of C6

1. **`add <plugin>`** runs `pnpm add` in `apps/server` (the plugins are dependencies of the server app, section 4.2), puts the name at the end of `plugins` in `bieberkit.config.ts` (the list is edited as text, in its own style, and the rest of the file is as the person wrote it), and resolves the graph with the real manifest of the plugin that was just installed: the same resolver as the scaffolder and the boot. If the graph does not resolve, the attempt is undone, the config as it was and the package removed again, and the error is the one of the resolver (`PLG_MISSING_REQUIRE`, `PLG_CONFLICT`, `PLG_DIALECT`...). A plugin that is listed already is `BK_ADD_ALREADY`. On success the keys of the plugin that have no default are added to `.env` as `KEY=` under a comment with its name, and `.env.example` is regenerated.
2. **`remove <plugin>`** lists what the plugin owns, which is the tables that its manifest lists (PLG-03, PLG-07). It works out the config, the migration and the answer first, runs `pnpm remove` before it writes anything, and writes the config and the migration after, so a pnpm that fails or a question that is cancelled leaves the project as it was. With data to drop and no `--yes` it asks when a person is there, and otherwise stops with `BK_REMOVE_CONFIRM_NEEDED` (exit code 2) and the tables in the message, before anything is touched. A plugin that another one requires is `BK_REMOVE_REQUIRED_BY`, and one that is not installed is `BK_REMOVE_NOT_INSTALLED`. Confirmed, it takes the entry out of the config, runs `pnpm remove`, regenerates `.env.example`, and writes `migrations/Migration<timestamp>_remove_<name>.ts` that drops the tables (`down` refuses and says to restore from a backup). The file carries `bieberkit-ignore BK_MIGRATION_DESTRUCTIVE` with its reason, so `bieberkit check migrations` passes on a drop that was confirmed and says why (DATA-02, DATA-08). The migration is run by the migrator of M1.8.
3. **The package manager is not bypassed.** A `pnpm` that fails is `BK_PNPM_FAILED`, and its fix says that the settings of the supply chain are never relaxed to make an install pass (SEC-11).
4. **The Oxlint plugin** is `bieberkit/oxlint`, a plugin in the shape that Oxlint loads (`jsPlugins`; it is a default export, the one in the framework, because Oxlint requires it). Each rule is a rule of `bieberkit check` that reads one file (`headers`, `env-access`, `boundaries`, `orm`, `sql`, `transactions`), run by the same function, so the editor, `oxlint` and `bieberkit check` cannot disagree, and a test compares them. `generate` writes `.bieberkit/oxlintrc.json` with the plugin, the six rules, and the root, the author and the license of the project: `oxlint -c .bieberkit/oxlintrc.json`. A diagnostic carries the code (`BK_ENV_ACCESS`), the message, the fix and the line. The rules that need the application (`routes`, `generated`) and the files of the project (`migrations`) are not in the plugin. JS plugins of Oxlint are in alpha and not subject to semver, so the version of Oxlint is pinned by the project and a test runs the real binary.
5. **A copy of core of its own.** A plugin may bring its own copy of `@bieberkit/core`, whose errors are not `instanceof` ours, so a failure is read by its stable code and not by its class.

## Behavior of C7

1. **`migrate:make [name]`** writes `migrations/Migration<timestamp>[_name].ts` for what the entities changed since `migrations/.snapshot-<dialect>.json`, and says its path. It never reads the live database (ADR 0008). A change that drops, renames or narrows something is written and reported as a warning, and the file is checked in `check`. Nothing to make is a success.
2. **`migrate`** opens the migrator on `MIGRATE_DATABASE_URL` (DATA-25), under the lock, and runs the steps of the framework and of the plugins in boot order, then the files of the project. A refused step (`PLG_CONTRACT_SAME_DEPLOY`) is `BK_MIGRATE_REFUSED` and stops the run before the files. A file with a destructive statement stops the run with `DATA_MIGRATION_DESTRUCTIVE` until `--allow-destructive` is given in the contract release (DATA-08). `--status` lists the files and the steps that ran and that wait, and runs nothing. `--rollback` reverts the last file and never a plugin step (steps only go forward, DATA-24). The two flags together are `BK_USAGE_FLAGS_CONFLICT`. The migrate role of `bieberkit start migrate` does the same in production, and in development it keeps making the tables of the entities from the metadata, so the loop is fast.
3. **`build`** regenerates everything (GEN-02), runs `pnpm exec tsc --noEmit` when the project has a `tsconfig.json` (`--no-typecheck` skips it; a failure is `BK_BUILD_TYPECHECK`), and writes the standalone Ajv validators and fast-json-stringify serializers to `apps/server/dist/standalone/` (SCH-06). The bundle of the server and the builds of the admin and of the site wait for M1.8's admin and for the image of M1.9.
4. **`check plugin-steps`** reads the steps that plugins contribute: a drop or a rename in a step that is not a `contract` step is `BK_STEP_DESTRUCTIVE` (an error), a `contract` step with no `after` is `BK_STEP_CONTRACT_NO_AFTER` (a warning, because the migrate role cannot refuse it in the deploy of its expand step, DATA-08), and on MySQL a step with two or more DDL statements and one without `ifNotExists()` or `ifExists()` is `BK_STEP_MYSQL_UNGUARDED` (a warning, DATA-27). **`check plugin-tables`** (PLG-02) reads the files of a plugin package that lives in the project and refuses what it queries of another plugin: `BK_PLUGIN_TABLE_QUERY` for a table of another plugin (from its static manifest) that is a literal in `selectFrom`, `insertInto`, `updateTable`, `deleteFrom`, a join or `from`, or in SQL text of the `sql` tag, `sql.raw`, `.raw`, `.execute` and `.query`, and `BK_PLUGIN_ENTITY_QUERY` for an entity that the file imported from another plugin and gave to the entity manager (`find`, `findOne`, `count`, `createQueryBuilder`, `getRepository`, ...). It does not see a computed table name, `classOf(em, name)` or a table that a variable holds. The tables of the framework and of `@bieberkit/auth` are not a plugin's, and the code of the project is not read. It is a static check and no sandbox (PLG-04). It reads the plugins from their `package.json` and imports none, so it does not load the application, but the Oxlint plugin does not offer it. **`check scoped-permissions`** runs `checkScopedPermissions` of `@bieberkit/auth` on the conditions of every module (`BK_AUTHZ_SUBJECT_UNKNOWN`, `BK_AUTHZ_ACTION_INVALID`, `BK_AUTHZ_CONDITION_THROWS`, `BK_AUTHZ_CONDITION_NOT_ALLOWED`, AUTHZ-06). Both load the application, so the Oxlint plugin does not offer them.

## The admin and the plugins of a project (UI-37, UI-38)

- `bieberkit dev` serves `apps/admin` with its Vite (`--admin-port`, 5173), gives the server that address as `ADMIN_URL` through `.bieberkit/dev.env`, and regenerates the files when `apps/server/src` or `plugins/*/src` change.
- `bieberkit build` checks the types of the project, of `apps/admin` and of `plugins/*/src/admin`, writes the standalone files, and builds the admin with Vite.
- `bieberkit/admin-vite` is the Vite plugin of `apps/admin`: it lists the admin parts in the boot order of the plugins, reads them with a module runner of the Vite of the project, stops on every mistake of a part (`BK_ADMIN_PART_INVALID`) and on two copies of a shared package (`BK_ADMIN_TWO_COPIES`). `bieberkit check` lets only a `vite.config` file import it.

## Plugin manifest builds (M2.1 H1, PLG-07)

In a plugin package, `bieberkit build` derives the static `bieberkit` field of `package.json` from the default-exported plugin definition, with the runtime key collectors. It does not load an application config, read application environment keys, boot a process, migrate or seed a database. It preserves the package's identity, exports and other metadata, and atomically replaces the JSON only after validation.

The nearest package is recognized by a standard scoped `plugin-`/`bieberkit-plugin-` name, an unscoped `bieberkit-plugin-` name, or the `bieberkit-plugin` keyword. Entry selection accepts a string main export, the `.` export with `@bieberkit/source`, `import`, `node` or `default` conditions, or `main`. The entry must exist inside the package. A plugin's compiler remains its normal build tool; first-party plugin scripts run tsdown and then manifest generation.

`bieberkit build --check` is read-only verification in a plugin package. Missing, stale or mismatched metadata fails with `PLG_MANIFEST_MISSING`, `PLG_MANIFEST_STALE`, `PLG_MANIFEST_NAME` or `PLG_MANIFEST_VERSION`. Object-key and key-list order alone do not make a manifest stale, but duplicate or changed list values do. A normal application `build` keeps its previous behavior; `build --check` in an application is `BK_USAGE_PLUGIN_CHECK` (exit 2), not a build that writes files.

Other build diagnostics are `BK_PLUGIN_PACKAGE` (invalid package identity), `BK_PLUGIN_ENTRY` (missing or invalid declared entry), `BK_PLUGIN_IMPORT` (definition import failure), `BK_PLUGIN_NOT_EXPORTED` (the entry is not a plugin), and `BK_PLUGIN_MANIFEST_WRITE` (filesystem failure). They identify the package or entry and leave its JSON unchanged on validation/import failure.

Repository commands:

- `pnpm manifests:write` regenerates first-party package fields and the bundled index. The index is generated source and is never edited by hand.
- `pnpm check:manifests` verifies package fields and the bundled index without repairing them. It runs inside `pnpm check`, including existing CI jobs.
- `pnpm build` regenerates manifests before the workspace build. Each first-party plugin build also refreshes its own field; generator/checker inputs participate in Turbo cache hashes.
- `pnpm test:artifacts` runs after `pnpm build`. It checks actual plugin tarballs and runs the packed scaffolder's graph resolver for all three dialects with no runtime plugin packages installed. It is separate from source-level unit tests because it checks built output.

Metadata loading and collection are available to tools through `@bieberkit/server/plugins` without loading runtime adapters. No public entity or plugin-definition signature changes in H1.
